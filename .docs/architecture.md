# Архитектура и принципы проектирования

## Особенности работы с фреймворком ERGOMS

### Модульная архитектура и Git submodules
- Архитектура системы задаётся манифестом `.gitmodules`: ядро и каждый доменный модуль подключаются посредством механизма Git submodule, обеспечивая независимую разработку компонентов и выборочное обновление через `git submodule update`.
- Ядро образуется субмодулями `core/api`, `core/client`, `core/media_api`, а также форками `core/django` и `core/django_rest_framework`. В последних удалён функционал стандартной административной панели Django ввиду отсутствия необходимости её использования.
- Каждая директория `modules/<имя>` представляет собой обособленный submodule (например, `modules/video_analysis`, `modules/crm`). Модули взаимодействуют с ядром через унифицированный API-контракт и клиентский интерфейс, сохраняя изоляцию, что обеспечивает упрощённую поддержку и масштабируемость.

### Модульные переменные окружения
- Каждый модуль располагает собственным файлом `.env`, размещённым в корневой директории модуля совместно с каталогами `api` и `client`. Фреймворк осуществляет адаптивное объединение модульных переменных окружения с глобальными настройками, вследствие чего требуется описание исключительно отличий от базовой конфигурации.

### Структура модулей
- Базовая структура модуля образуется парой каталогов `api` и `client`. В файле `api/apps.py` реализуется класс `AppConfig`, осуществляющий регистрацию модуля, конфигурацию путей к пакетам, переключение режимов GPU/CPU и подключение сигналов. Используются стандартизированные пути, определённые в `core/api/src/config/settings/base.py`.
- Для фоновых задач формируются файлы `celery_config.py` и `celery_beat_config.py`, расширяющие класс `CeleryModuleConfig`. В них декларируются маршруты задач, очереди обработки и расписания выполнения без внесения изменений в ядро системы.

### Модели и миграции
- Определение таблиц и связей осуществляется в файле `models.py`. Миграции генерируются стандартными командами Django либо ERGO CLI, при этом проектирование моделей производится с соблюдением нормальных форм реляционных баз данных и учётом зависимостей между модулями.

### Задачи Celery
- Файл `tasks.py` импортируется системой Celery автоматически при инициализации воркеров. В нём располагаются пайплайны обработки данных, включая высоконагруженные задачи, масштабируемые посредством Celery с учётом параметров GPU/CPU, определённых в `apps.py`.

### Клиентская архитектура
- Фронтенд-файлы `client/js/endpoints.js`, `client/js/routes.js` и `client/js/menu-config.json` обнаруживаются фреймворком автоматически: они формируют точки входа API, регистрируют маршруты клиентского приложения и определяют элементы навигационного меню без необходимости модификации ядра.
- Vue-компоненты подлежат декомпозиции: бизнес-логика выделяется в файлы `.js` либо `.ts`, стилевое оформление — в `.scss`. Для зависимостей ядра применяются абсолютные импорты с префиксом `@/`, обеспечивая модульную изоляцию.

### Интеграция с Cursor
- Фреймворк обеспечивает совместимость с MCP-инфраструктурой Cursor. Реестр серверов и параметры подключения задаются в файле `.cursor/mcp.json` (детальное описание приведено в разделе «Конфигурационные файлы»).

### Правила разработки Cursor (Rules)

Система правил Cursor представляет собой механизм формализации стандартов кодирования, архитектурных паттернов и конвенций проекта, обеспечивающий консистентность разработки при взаимодействии с AI-ассистентом.

#### Назначение системы правил

Правила Cursor решают следующие задачи:

- **Унификация стиля кода**: автоматическое применение соглашений о форматировании, именовании и структуре кода
- **Контекстуализация AI**: предоставление ассистенту специфичной информации об архитектуре проекта, используемых паттернах и ограничениях
- **Предотвращение ошибок**: автоматическое напоминание о критичных требованиях (использование миксинов, запрет на определённые действия)
- **Ускорение разработки**: исключение необходимости повторного объяснения базовых правил проекта при каждом взаимодействии
- **Передача знаний**: документирование неочевидных архитектурных решений и специфичных требований проекта

#### Структура каталога правил

Правила системы располагаются в каталоге `.cursor/rules/` и организованы по доменным областям:

```
.cursor/rules/
├── api_code.mdc          # Правила разработки серверной части (Django)
├── client_code.mdc       # Правила разработки клиентской части (Vue.js)
├── code.mdc              # Общие правила кодирования
├── database.mdc          # Правила работы с базами данных
├── django.mdc            # Специфичные правила Django
├── docs.mdc              # Правила генерации документации
├── mcp.mdc               # Правила использования MCP-серверов
├── oc.mdc                # Правила кроссплатформенной разработки
├── struct.mdc            # Правила архитектурной организации
└── word_docs.mdc         # Правила работы с документами Word
```

#### Формат файлов правил

Правила определяются в файлах формата `.mdc` (Markdown with metadata) со следующей структурой:

```markdown
---
alwaysApply: true
---

# Заголовок раздела

Описание правил и требований в формате Markdown.
```

**Метаданные front matter:**

- `alwaysApply: true` — правило применяется автоматически при каждом взаимодействии с ассистентом без необходимости явного упоминания

#### Классификация правил по доменам

**Архитектурные правила (`struct.mdc`):**
- Описание модульной структуры системы (ядро + модули)
- Принципы изоляции компонентов
- Соглашения об организации файловой структуры

**Правила серверной разработки (`api_code.mdc`, `django.mdc`):**
- Использование обязательных миксинов (например, `SwaggerSafeMixin`)
- Работа со стандартными путями системы
- Запрет на генерацию административной панели Django

**Правила клиентской разработки (`client_code.mdc`):**
- Соглашения об импортах (абсолютные для ядра, относительные для модулей)
- Использование компонентов Bootstrap и библиотеки иконок Lucid
- Декомпозиция компонентов, стилей и логики
- Локализация интерфейса на русском языке

**Правила работы с данными (`database.mdc`):**
- Использование Django ORM и SQLAlchemy
- Создание таблиц посредством миграций
- Паттерны работы со сложными SQL-запросами

**Правила кодирования (`code.mdc`):**
- Ограничение размера файлов (максимум 700 строк)
- Применение принципов ООП и SOLID
- Использование Celery для высоконагруженных алгоритмов
- Адаптация под GPU/CPU

**Правила интеграции (`mcp.mdc`):**
- Использование MCP-серверов для работы с API, базой данных и файловой системой

**Правила кроссплатформенности (`oc.mdc`):**
- Обеспечение совместимости с Windows и Linux

**Правила документирования (`docs.mdc`, `word_docs.mdc`):**
- Запрет на автоматическую генерацию документации
- Использование метрической системы измерений в Word-документах

#### Создание новых правил

Для добавления пользовательского правила:

1. Создайте файл `.mdc` в каталоге `.cursor/rules/`:
   ```bash
   touch .cursor/rules/custom_rule.mdc
   ```

2. Определите структуру правила:
   ```markdown
   ---
   alwaysApply: true
   ---
   
   ### Заголовок правила
   
   Описание требований и примеры использования.
   ```

3. Сохраните файл — правило будет автоматически применяться при следующем взаимодействии с Cursor

**Рекомендации по формулировке правил:**

- Используйте императивную форму для требований («Используй», «Не генерируй», «Всегда применяй»)
- Предоставляйте примеры кода для иллюстрации правил
- Группируйте связанные правила в тематические разделы
- Избегайте избыточной детализации — правила должны быть лаконичными и понятными

#### Применение правил в рабочем процессе

Правила применяются автоматически при каждом обращении к AI-ассистенту благодаря флагу `alwaysApply: true`. Система правил обеспечивает:

- **Контекстную релевантность**: ассистент учитывает специфику проекта при генерации кода
- **Консистентность**: автоматическое следование установленным конвенциям
- **Предотвращение регрессий**: напоминание о критичных ограничениях и требованиях

**Преимущества централизованной системы правил:**

- Отсутствие необходимости повторного объяснения базовых требований
- Синхронизация стандартов кодирования между разработчиками команды
- Документирование архитектурных решений в машиночитаемом формате
- Упрощение онбординга новых участников проекта

### Средства разработки
- Конфигурация интегрированных сред разработки VS Code и Cursor поставляется в составе репозитория. Файлы `.vscode/settings.json`, `.vscode/tasks.json` и `.vscode/extensions.json` определяют воспроизводимую рабочую среду, исключая необходимость ручной настройки (полное описание представлено в разделе «Конфигурационные файлы»).

### Платформенная совместимость
- Система использует унифицированный набор команд развёртывания для операционных систем Windows и Linux. Сценарии, расположенные в `core/deployment/windows` и `core/deployment/linux`, обеспечивают идентичную конфигурацию сервисов, вследствие чего ERGO MS функционирует кроссплатформенно без различий в реализации бизнес-логики и API.

### Управление окружением
- Каталог `virtual_env/` структурирует вспомогательные ресурсы системы: подкаталог `python/` содержит изолированные виртуальные среды Python, `nodejs/` — локальные пакеты Node.js, `celery/` — артефакты очередей сообщений, `trained_models/` — предобученные модели машинного обучения, каталоги `packages/`, `static_api/`, `resources/` — дополнительные данные и статические объекты. Данная стратификация исключает конфликты между модулями и упрощает перенос установки на иное оборудование.

### Модульность библиотек
- Манифест `package.json` определяет npm-рабочие пространства (`core/client`, `modules/*/client`), обеспечивая независимую установку клиентских зависимостей для ядра и каждого модуля в отдельности.
- Конфигурация Poetry (`pyproject.toml`) описывает Python-зависимости: компоненты ядра подключаются посредством локальных пакетов (`core/api`, `core/django`, `core/django_rest_framework`), каталоги `modules/*` экспортируют API-интерфейсы модулей. Дополнительные источники пакетов (`pytorch-cu128`) обеспечивают гибкое управление GPU-зависимостями.

### Командная оболочка ergoms

Утилита `ergoms` представляет собой центральную командную оболочку системы ERGO MS, обеспечивающую единый интерфейс для управления всеми компонентами системы и выполнения операций развёртывания.

#### Архитектура и принципы работы

**Кроссплатформенность:**
- Утилита автоматически определяет операционную систему и использует соответствующий интерпретатор
- Windows: PowerShell скрипты из `core/deployment/windows/ergo_ms.ps1`
- Linux: Bash скрипты из `core/deployment/linux/ergo_ms.sh`
- Команды с префиксами `win:` и `linux:` автоматически фильтруются по платформе

**Модульная архитектура команд:**
- Центральный файл конфигурации: `core/deployment/commands.conf` — определяет команды ядра системы
- Модульные конфигурации: `modules/<имя>/ergoms.conf` — расширяют CLI специфичными командами модулей
- Автоматическая регистрация: модульные команды регистрируются с префиксом имени модуля (`module_name:command_name`)

**Контекст выполнения команд:**
- `poetry:` — команды Poetry выполняются в корне проекта с автоматической активацией виртуального окружения
- `api:` — команды Django manage.py выполняются в директории `core/` с активированным виртуальным окружением
- `npm:` — команды npm выполняются в корне проекта (требуют наличие `package.json`)
- `shell:` — обычные shell-команды выполняются в корне проекта (кроссплатформенные)
- `win:` / `linux:` — платформо-специфичные команды, автоматически фильтруются

**Составные команды:**
- Использование оператора `&&` для объединения нескольких команд в цепочку
- При ошибке в одной команде цепочка прерывается с кодом возврата ошибки

#### Установка и настройка

**Установка CLI-обёртки:**

```bash
# Windows (PowerShell с правами администратора)
.\core\deployment\windows\ergo_ms.ps1 install-cli

# Linux (Bash с правами root)
sudo bash core/deployment/linux/ergo_ms.sh install-cli
```

**Проверка установки:**

```bash
ergoms help
```

#### Структура конфигурационных файлов

**Формат определения команды в `commands.conf`:**

```conf
# Комментарий
command-name=type:command

# Составная команда
complex-command=command1 && command2 && command3
```

**Примеры конфигурации:**

```conf
# Простые команды
python-install=poetry:install
db-migrate=api:migrate
client-build=npm:run build

# Составные команды
migrate-all=api:makemigrations && api:migrate
setup=poetry:install && npm:install && api:migrate

# Платформо-специфичные команды
setup-full=win:powershell -File core/deployment/windows/ergo_ms.ps1 setup-full && linux:bash core/deployment/linux/ergo_ms.sh setup-full
```

#### Модульные команды

Каждый модуль может расширять CLI посредством файла `modules/<имя>/ergoms.conf`:

**Пример модульной конфигурации (`modules/video_analysis/ergoms.conf`):**

```conf
# Установка всех зависимостей модуля
install=api:install_ffmpeg && api:install_opus_mt && api:install_vosk_model

# Избирательная установка компонентов
install-ffmpeg=api:install_ffmpeg
install-opus=api:install_opus_mt
install-vosk=api:install_vosk_model
install-tts-fr=api:install_tts_fr
```

**Вызов модульных команд:**

```bash
# Квалифицированный вызов (рекомендуется)
ergoms video_analysis:install
ergoms video_analysis:install-ffmpeg

# Неквалифицированный вызов (при отсутствии коллизий имён)
ergoms install-ffmpeg
```

#### Прокси-команды

Утилита поддерживает прямую переадресацию к инструментальным утилитам без необходимости определения в конфигурации:

```bash
# Переадресация к Poetry
ergoms poetry install
ergoms poetry add <package>
ergoms poetry update

# Переадресация к Django manage.py
ergoms api migrate
ergoms api createsuperuser
ergoms api shell

# Переадресация к npm
ergoms npm install
ergoms npm run dev
ergoms npm run build
```

**Подробное описание всех доступных команд см. в разделе [Управление сервисами через CLI](cli.md).**

#### Расширение функциональности

**Создание новых команд:**

1. Откройте файл `core/deployment/commands.conf`
2. Добавьте определение команды в формате `command-name=type:command`
3. Сохраните файл — команда будет доступна немедленно

**Пример добавления команды:**

```conf
# Новая команда для очистки кеша
clear-cache=api:clear_cache && shell:rm -rf .cache
```

**Создание модульных команд:**

1. Создайте файл `modules/<имя_модуля>/ergoms.conf`
2. Определите команды модуля
3. Команды автоматически регистрируются с префиксом модуля

#### Диагностика и отладка

**Просмотр доступных команд:**

```bash
ergoms help
```

**Проверка конфигурации:**

Утилита автоматически загружает команды из:
1. `core/deployment/commands.conf` (ядро)
2. `modules/*/ergoms.conf` (модули)

При отсутствии команды выводится список доступных команд и рекомендация использовать `ergoms help`.

**Обработка ошибок:**

- При отсутствии виртуального окружения для `api:` команд выводится сообщение об ошибке
- При отсутствии `package.json` для `npm:` команд выводится сообщение об ошибке
- При ошибке в составной команде цепочка прерывается с соответствующим кодом возврата

#### Интеграция с системой разработки

Утилита `ergoms` интегрирована с задачами VS Code/Cursor (`.vscode/tasks.json`), что позволяет использовать команды через интерфейс IDE:

```
Ctrl+Shift+P → Tasks: Run Task → <command-name>
```

Все команды из `commands.conf` автоматически доступны как задачи VS Code.

### Django-автоматизация в рамках ERGOMS

Фреймворк предоставляет набор утилит (`core/api/src/core/utils`), упрощающих работу с Django и Celery:

#### Автоматическое обнаружение приложений

Модуль `core/utils/auto_api/auto_config.py` рекурсивно сканирует директории `core` и `modules`, автоматически регистрирует Django-приложения с файлом `apps.py` в `INSTALLED_APPS` и собирает URL-паттерны из `urls.py`. Это исключает ручное добавление модулей в настройки.

#### Модульная конфигурация Celery

Система `core/utils/celery` позволяет каждому модулю определить собственный `celery_config.py`, наследующий `CeleryModuleConfig`. В нём описываются:
- `get_task_routes()` — маршруты задач модуля в очереди.
- `get_task_queues()` — определение exchange и routing_key.
- `get_task_annotations()` — таймауты, лимиты для конкретных задач.
- `get_module_loggers()` — специализированные логгеры (`celery.module.<имя_модуля>.<логгер>`).

Менеджер `CeleryModuleManager` автоматически обнаруживает конфигурации в `modules/*/celery_config.py`, применяет их в `config/celery.py`, создаёт файлы логов (`logs/modules/<имя>/<имя>.log`) и обеспечивает изолированное логирование задач.

#### Управление переменными окружения

Файл `config/env.py` загружает переменные из корневого `.env`, затем из модульных `.env` (приоритет выше). Утилиты `core/utils/environment/methods.py` сканируют `modules/*/` и `core/*/` на наличие `.env`, объединяя их в единый контекст. Это позволяет модулям переопределять глобальные настройки локально.

#### Работа с базами данных

Модуль `core/utils/database` предоставляет:
- `DBConfig` — парсинг `databases.yaml`, поддержка SSH-туннелей для удалённых БД.
- `SqlAlchemyManager` — выполнение SQL-запросов вне ORM, подключение к множественным источникам (PostgreSQL, MySQL, ClickHouse, MSSQL и др.).
- Структурированные типы соединений (`types.py`) для безопасной работы с конфигурацией.

Рекомендуется создавать `queries.py` в модулях с SQL-шаблонами, передавая их в `SqlAlchemyManager` для выполнения сложных аналитических запросов.

#### Вспомогательные методы и миксины

- `core/utils/methods.py`:
  - `parse_errors_to_dict()` — преобразование ошибок валидации Django в словарь.
  - `send_confirmation_email()` — отправка кодов подтверждения с логированием SMTP-ошибок.
  - `convert_snake_to_camel()`, `convert_path_to_dot_notation()` — утилиты форматирования.

- `core/utils/mixins.py`:
  - `SwaggerSafeMixin` — предотвращает ошибки генерации Swagger при фильтрации queryset по пользователю. Используйте в ViewSet'ах, которые фильтруют данные по `request.user`, чтобы избежать сбоев при построении документации.

### Vue.js-автоматизация в рамках ERGOMS

Клиентская часть фреймворка реализует систему автоматического обнаружения и оркестрации модулей на основе класса `ModuleManager`, обеспечивающего централизованное управление маршрутизацией, навигационным меню, API-эндпоинтами и визуальными компонентами.

#### Архитектура модульной системы

Система построена на принципе иерархической композиции менеджеров:

- **ModuleManager** (`core/client/src/modules/ModuleManager.js`) — центральный оркестратор, координирующий работу специализированных менеджеров:
  - `RouteManager` — управление маршрутами Vue Router
  - `MenuManager` — формирование структуры навигационного меню
  - `EndpointManager` — агрегация API-эндпоинтов
  - `IconManager` — регистрация визуальных компонентов иконок
  - `SeparatorManager` — управление разделителями меню

#### Механизм автоматического обнаружения модулей

При инициализации системы `ModuleManager` рекурсивно сканирует директории `core/client/src` и `modules/*/client/src`, обнаруживая следующие конфигурационные дескрипторы:

1. **`js/routes.js`** — определение маршрутов модуля для Vue Router
2. **`js/menu-config.json`** — конфигурация элементов навигационного меню
3. **`js/endpoints.js`** — экспорт API-эндпоинтов модуля
4. **`components/icons/`** — каталог пользовательских иконок модуля

Обнаруженные конфигурации автоматически агрегируются в единую структуру без необходимости явной регистрации в коде ядра системы.

#### Процесс инициализации

```javascript
// Инициализация менеджера модулей с конфигурацией порядка меню
const moduleManager = new ModuleManager({
  menuOrder: menuOrderConfig
})

// Параллельная инициализация всех менеджеров
await moduleManager.initialize()

// Генерация маршрутов для Vue Router
const routes = await moduleManager.generateAllRoutes(coreRoutes)

// Формирование конфигурации меню
const menuConfig = await moduleManager.getMenuConfig()
```

#### Валидация и диагностика

Система предоставляет встроенные механизмы валидации конфигураций:

```javascript
// Валидация всех конфигураций модулей
const validation = await moduleManager.validateAll()
// Возвращает: { isValid, routes, menu, endpoints }

// Получение статистики по модулям
const stats = await moduleManager.getStatistics()
// Возвращает количество маршрутов, элементов меню, эндпоинтов и т.д.
```

#### Преимущества архитектуры

- **Изоляция модулей**: каждый модуль определяет собственные маршруты, меню и API независимо от ядра
- **Декларативная конфигурация**: использование JSON-дескрипторов вместо императивного кода
- **Автоматическая регистрация**: отсутствие необходимости ручного добавления модулей в центральную конфигурацию
- **Горячая перезагрузка**: поддержка обновления конфигураций в режиме разработки без перезапуска системы
- **Кеширование**: оптимизация производительности посредством интеллектуального кеширования обнаруженных конфигураций

### Интеграция Bootstrap и стилевая архитектура

Система клиентского приложения использует архитектуру SCSS-модулей с интегрированным фреймворком Bootstrap 5, обеспечивающую консистентное визуальное оформление и адаптивную вёрстку.

#### Структура стилевых модулей

Централизованная стилевая система располагается в каталоге `core/client/src/scss/` и организована следующим образом:

- **`_variables.scss`** — глобальные переменные дизайн-системы (размеры, отступы, радиусы, анимации)
- **`_colors.scss`** — палитра цветов и тематические переменные
- **`_theme.scss`** — определение светлой и тёмной тем оформления
- **`_mixins.scss`** — переиспользуемые SCSS-миксины для типовых паттернов
- **`_globals.scss`** — глобальные стили HTML-элементов и утилитарных классов
- **`_overrides.scss`** — переопределение стандартных стилей Bootstrap
- **`_scrollbar.scss`** — кастомизация полос прокрутки
- **`styles.scss`** — главная точка входа, импортирующая все модули

#### Интеграция Bootstrap

Bootstrap импортируется после определения пользовательских переменных, что позволяет переопределить стандартные параметры фреймворка:

```scss
@import './_colors.scss';
@import './_theme.scss';
@import './_variables.scss';
@import './_overrides.scss';

@import 'bootstrap/scss/bootstrap';
```

Такая последовательность обеспечивает:

1. Применение кастомных переменных к компонентам Bootstrap
2. Переопределение стандартных стилей без модификации исходного кода фреймворка
3. Сохранение совместимости с обновлениями Bootstrap

#### Преимущества использования Bootstrap

- **Адаптивная сетка**: встроенная система сеток обеспечивает корректное отображение на устройствах различных размеров
- **Унифицированные компоненты**: стандартизированные UI-элементы (кнопки, формы, модальные окна) с консистентным поведением
- **Утилитарные классы**: обширная библиотека классов для быстрого прототипирования интерфейсов
- **Тематизация**: возможность глобального изменения визуального стиля посредством модификации SCSS-переменных
- **Доступность**: соответствие стандартам WCAG для создания инклюзивных интерфейсов

#### Модульная архитектура стилей

Каждый модуль системы располагает возможностью определения собственных стилей в файлах `*.scss`, которые автоматически интегрируются в общую систему при сборке проекта. Это обеспечивает инкапсуляцию стилей и предотвращает конфликты именования.

### Агрегация переиспользуемых компонентов

Каталог `core/client/src/components/` содержит библиотеку универсальных Vue.js-компонентов, предназначенных для упрощения разработки пользовательских интерфейсов модулей системы.

#### Классификация компонентов

**Диалоговые компоненты:**

- **`ConfirmDialog.vue`** — модальное окно подтверждения операций с настраиваемыми заголовком, сообщением и кнопками действий
- **`ChoiceDialog.vue`** — диалог выбора из множества опций с поддержкой радиокнопок и чекбоксов
- **`ModalCenter.vue`** — базовый компонент центрированного модального окна с управлением жизненным циклом

**Компоненты форм и ввода данных:**

- **`SelectBox.vue`** — кастомный выпадающий список с поддержкой поиска, множественного выбора и виртуализации
- **`DropDown.vue`** — универсальный выпадающий список с настраиваемым контентом
- **`TableEditor.vue`** — табличный редактор данных с inline-редактированием и валидацией

**Навигационные компоненты:**

- **`NavigationButtons.vue`** — группа кнопок навигации с поддержкой состояний (активная, неактивная, disabled)
- **`menu/`** — набор компонентов для построения многоуровневого навигационного меню
- **`header/`** — компоненты шапки приложения (профиль пользователя, настройки, уведомления)

**Уведомления:**

- **`NotificationProvider.vue`** — провайдер системы уведомлений с управлением очередью сообщений
- **`NotificationToast.vue`** — визуальный компонент всплывающего уведомления

**Прочие утилитарные компоненты:**

- **`DefaultAvatar.vue`** — генератор аватаров по умолчанию на основе инициалов пользователя
- **`NotFound.vue`** — страница ошибки 404

#### Принципы разработки компонентов

1. **Переиспользуемость**: компоненты проектируются для использования в различных контекстах без модификации
2. **Параметризация**: расширенная система входных параметров (props) для настройки поведения и внешнего вида
3. **Событийная модель**: использование событий Vue.js для коммуникации с родительскими компонентами
4. **Слоты**: поддержка слотов для инжекции пользовательского контента
5. **Композиционная архитектура**: декомпозиция сложных компонентов на более простые составляющие
6. **Реактивность**: использование Composition API для оптимального управления реактивным состоянием

#### Интеграция в модули

Компоненты доступны модулям посредством абсолютных импортов с префиксом `@/components/`:

```javascript
import ConfirmDialog from '@/components/ConfirmDialog.vue'
import SelectBox from '@/components/SelectBox.vue'
import NotificationProvider from '@/components/NotificationProvider.vue'
```

Такая архитектура исключает дублирование кода между модулями и обеспечивает консистентный пользовательский опыт во всех компонентах системы.
