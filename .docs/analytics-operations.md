# Аналитические операции: поставка D1

Текущее состояние после D2: зависимости источников выделены отдельной серией,
чистая поставка из HEAD принята в контуре PostgreSQL/CPU. Состав, проверки и
границы — [analytics-source-delivery.md](analytics-source-delivery.md).
Ниже сохранён исторический срез D1.

Срез 25.10.2026. Новый контур реализован для EDA, линейной регрессии,
ARIMA, SARIMA и boxplot. Работы выполнялись локально. Старые отчёты остаются
архивом в исходных таблицах, без копирования и пересчёта.

## Историческая граница самостоятельной поставки D1

При приёмке D1 полная рабочая копия содержала незакоммиченный общий исполнитель
`modules/bi_analysis/api/bi_datasets/services/query_executor.py` и связанные
исправления источников. Они принадлежат сохранённому локальному остатку
стабилизации и не включаются в D1.

Исполнитель из прежнего HEAD загрузчика EDA использовал основную БД.
Новый runtime не вызывает этот путь: строит запрос общим `build_dataset_query`,
вызывает source-aware `DatasetQueryExecutor`, затем `core.analytics.tables.rows_to_frame`.
Если общего исполнителя нет, API возвращает **503 `dataset_runtime_unavailable`**
до создания/публикации запуска. Worker проверяет зависимость повторно.
Ошибки выбранного источника не включают fallback к одноимённой таблице основной БД.

Поэтому на D1 этап D оценивался в ≈90%: код, архив, UI и работающий сквозной
контур были проверены, но самодостаточная поставка запуска из датасета требовала
разбора и согласованного включения остатка источников. Этот разбор выполнен в D2;
необходимые изменения источников проверены и закоммичены отдельно.

## Ответственность ядра и BI

`core.analytics.operations` содержит независимый реестр и дескрипторы.
Импорт каталога не импортирует Django, Polars, NumPy или Torch.
Расчёт получает DataFrame, JSON-параметры и callback прогресса. Дескриптор
содержит id, версию, название, категорию, схемы входа/параметров/выхода,
`result_kind`, Python-группы, инструменты, модели и ресурсы.

Параметры проверяются до публикации; неизвестные ключи, неверные типы,
повторяющиеся поля и недопустимые границы отклоняются. Поддерживаемые v1-типы
параметров: непустая строка, целое с границами, массив имён колонок.
Числовые библиотеки импортируются только при выполнении операции.
Готовые математические функции C используются без замены алгоритмов.

Ядро регистрирует три platform-op и читает JSON-группу backend-провайдеров.
Не импортирует BI и не владеет его источниками или ACL. BI реализует backend,
единую Celery-задачу и одну новую модель `AnalysisRun`. Модель находится
в отдельном приложении `bi_analysis_operations`: миграция зависит от уже
зафиксированной `0020_dataset_public_id` и пользователя, не от чужой `0008`.
Таблицы ядра и старых отчётов не меняются.

## Bridge-контракт v1

| Имя | Параметры и результат |
|---|---|
| `core.analytics.backends` | Группа `{provider: {catalog, run, status}}`; значения — имена ops, сериализуемые в JSON |
| `core.analytics.list_operations` | Необязательный `provider`; возвращает массив дескрипторов. С provider каталог читается у соответствующего backend |
| `core.analytics.run_operation` | `provider`, `operation_id`, `input_ref`, `parameters`, `user_public_id`/локальный `user`; возвращает `{ok, created, run}` либо `{ok: false, error}` |
| `core.analytics.get_status` | `provider`, `run_id`, субъект; возвращает `{ok, run}` либо контролируемую ошибку |

BI регистрируется под ключом `bi_analysis`, ops `bi.analytics.catalog`,
`bi.analytics.run`, `bi.analytics.status`. HTTP-маршрутизация описана
в `api/bridge_manifest.yaml`, включая прежние ops BI. Серверная часть моста
остаётся служебной: используется существующая защита internal bridge.
Субъект поступает от доверенного вызывающего сервиса; публичный HTTP API
подставляет аутентифицированного пользователя и не принимает его из тела запроса.

`input_ref` имеет форму `{kind: "dataset" | "artifact", public_id: "UUID"}`.
Пути, SQL и DataFrame через мост не передаются. Ссылка на артефакт разрешает
повторное использование проверенного снимка его инициатором с актуальными
правами на датасет и первоначальные источники.

Модуль может расширить реестр через свой существующий `integrations.py`:
`registry.register(Operation(...), executor)`. Дубликат id отклоняется.
Дескриптор и версия сохраняются в запуске; worker отказывает, если версия
недоступна. Backend и worker должны иметь согласованный состав операций.
Неизвестный клиенту вид результата отображается как экранированный JSON.

## Публичный API BI

Все пути ниже относительны `/api/bi_analysis/`, требуют аутентификации.

| Метод и путь | Вход | Успех | Ошибки |
|---|---|---|---|
| `GET operations/` | Нет | 200, массив дескрипторов | 401, 503 |
| `POST bi_datasets/<dataset UUID>/operations/` | `{operation_id, parameters?, artifact_id?}` | 202 `{ok, created: true, run}`; повтор активного запуска — 200 с прежним UUID | 400 параметры, 403 источники, 404 субъект/датасет/снимок, 503 очередь или executor |
| `GET bi_datasets/<dataset UUID>/operations/` | Нет | 200 `{runs}`: последние записи без содержимого результатов | 401, 404 |
| `GET bi_datasets/<dataset UUID>/operations/<run UUID>/` | Нет | 200 `{ok, run}` | 401, 404, 503 транспорт |
| `GET bi_datasets/<dataset UUID>/operations/archive/<reference>/` | `eda:<pk>`, `model:<pk>` либо имеющийся UUID старого отчёта | 200 `{ok, run}` с исходным результатом | 401, 404 |

`run` содержит UUID, id/версию/дескриптор операции, параметры, входную ссылку,
происхождение, статус, прогресс 0–1, результат, размер выборки, время и инициатора.
Статусы: `pending`, `running`, `completed`, `failed`. Ошибка выполнения возвращается
в статусе запуска как стабильный `error_code`; подробности остаются в журнале.
Неизвестный или чужой UUID не раскрывает результат, прогресс или исключение.
Идентификатор датасета из URL участвует в поиске запуска.

Список содержит до 50 новых запусков и по 50 записей каждого архивного типа.
Большие JSON-результаты исключены из SQL-выборки списка и запрашиваются отдельно.
Архивная ссылка читает любой соответствующий отчёт, независимо от лимита списка.
Если прежний отчёт уже имеет UUID, архив использует его; `eda:<pk>` и `model:<pk>`
остаются адаптерами старых идентификаторов. На составе без прежней UUID-миграции
сохраняется переходное чтение этих идентификаторов.
Прежние EDA/modeling URL и таблицы сохранены. Инициатор, даты, task_id, config,
результат и размер выборки старого отчёта не обновляются при чтении архива.
Для старых записей отсутствующая информация о снимке не реконструируется.

## Жизненный цикл и снимки

Запуск резервируется под блокировкой датасета. Fingerprint включает инициатора
через выборку активных запусков, операцию, версию, параметры, входную ссылку
и ревизию описания источников. Публикация происходит только после commit;
rollback не оставляет задачи. Ошибка брокера даёт 503, вычисления в HTTP не идут.

До публикации сохраняется происхождение и ревизия описания выбранных таблиц,
полей, параметров и файлов. Изменение описания в очереди или во время чтения
даёт `source_changed`. Данные внешней БД снимаются при работе worker, а не
в момент HTTP-запроса. Это не обещание распределённого snapshot isolation
между независимыми внешними источниками.

Worker повторно проверяет права, получает подготовленную таблицу и применяет
выборку после преобразований. Parquet сохраняется через существующий media_api.
Перед вычислением проверяются SHA256, формат, схема и число строк. Storage-путь
не выдаётся клиенту. Результат публикуется после повторной проверки прав.
Повторная доставка одной задачи не запускает вычисление второй раз.
Последняя ссылка на снимок удаляется после commit; rollback сохраняет файл.

Ожидание и выполнение ограничены по сохранённому статусу и heartbeat.
Новый task имеет отдельный CPU-footprint: 2048 MiB, CPU 1, без GPU,
`max_parallel: 1`; прежний чужой diff footprint не включён в коммит.

| Настройка окружения / одноимённая Django setting | По умолчанию |
|---|---:|
| `BI_ANALYTICS_QUEUE_WAIT_SECONDS` | 300 |
| `BI_ANALYTICS_MAX_AGE_SECONDS` | 3600 |
| `BI_ANALYTICS_MAX_ARTIFACT_BYTES` | 536870912 |

Переменные должны быть положительными целыми. Django setting имеет приоритет.
Размер выборки использует прежние `BI_ANALYSIS_EDA_SAMPLE_LIMIT` и
`BI_ANALYSIS_MODELING_SAMPLE_LIMIT`. Новый installer и новые зависимости не добавлены.

## Проверки и ограничения

- Полная рабочая копия: 20 регрессий нового контура и 218 тестов BI OK,
  пять прежних ожидаемых пропусков. Проверены очередь, конкуренция, rollback,
  роли/таблицы, отзыв прав, подстановка UUID, порча снимка, исходные ACL снимка,
  изменение ревизии и отсутствие source-aware runtime.
- 90 тестов библиотеки/дескрипторов OK на Windows и Linux; Linux использовал
  установленный math-профиль без Torch, без новой установки пакетов.
- Проверки чистого состава отделены от рабочей копии. Положительные lifecycle
  тесты предоставляют табличный loader; отсутствие executor в настоящем чистом
  составе проверяется отдельно и даёт 503 до публикации. Это не приёмка SQL
  источников самостоятельной поставки D1.
- На чистом составе прошли 20 регрессий операций, 12 прежних тестов bridge
  и 32 клиентских теста. В рабочем клиенте прошли 40 тестов. Запуск по имени
  пакета в архивной копии остановился до тестов с `_path_normpath … NoneType`;
  использовано полное имя файла. Причина пакетного discovery в D1 не исправлялась,
  дополнительных изменений ядра для обхода не потребовалось. В D2 установлена
  причина: QA-архиватор пропускал отслеживаемый `modules/__init__.py` обёртки.
  После исправления состава копии штатный discovery всего BI прошёл.
- Отдельный Windows solo-worker с частным SQLAlchemy/SQLite-брокером выполнил
  все пять операций. Чтение выбрало внешнюю PostgreSQL-БД вместо одноимённой
  таблицы основной QA-БД. Каталог, запуск и статус прошли через настоящий HTTP
  bridge по loopback, включая JSON-восстановление субъекта и прямой backend-op.
  Дубликатов нет; чужому пользователю возвращён 404. Контрольная сумма всех
  полей старых отчётов осталась прежней.
- Chrome проверил формы из дескрипторов, выбор полей регрессии и POST-параметры,
  очередь, архив, четыре вида результата, read-only, пустой каталог и ошибки.
  Это компонентная проверка на сохранённых ответах настоящего API с существующим
  API-клиентом; браузер не запускал настоящий новый расчёт в этом сценарии.
- ESLint рабочей копии BI: 0 ошибок, 436 прежних предупреждений. Новые файлы
  и изменённый импорт не вводят диагностик. Сборка ядра клиента и BI прошла
  в отдельной копии; другие модули в неё не входят. Осталось предупреждение
  о крупных chunks.
- Архитектурная проверка вернула те же пять замечаний к размерам документов CRM.
  Новых нарушений не найдено.

Журналы, ответы API, кандидат и контрольные суммы:
`virtual_env/cache/analytics-d1-20261025/`. QA использует отдельные БД и кэш;
это не production. Чужие изменения источников, ACL, миграций, manifest зависимостей
и правил коммитов сохранены. Наблюдавшиеся параллельные изменения LMS и
organizations учитываются отдельно и не включаются в D1.

Регрессии запускаются штатными командами в настроенном тестовом контуре PostgreSQL:

```text
ergoms api test modules.bi_analysis.api.operations.tests.test_runtime --noinput
ergoms api test modules.bi_analysis.api --noinput
ergoms npm --prefix <абсолютный путь>/modules/bi_analysis/client test
```

Для тестов создаются отдельные `test_ergo_*` БД. Живой HTTP/Celery-прогон
использовал дополнительно частный брокер, result backend, media и две БД
собственного UUID. Он не заменяет нагрузочные проверки и обычные команды выше
не воспроизводят этот отдельный сквозной сценарий автоматически.

MSSQL/ClickHouse, настоящий remote media_api, Linux Celery, Redis/RabbitMQ,
разные физические хосты, полный клиент всех модулей и нагрузочная матрица
этой поставкой не подтверждены. SSH, production, push и смена gitlinks не использовались.
