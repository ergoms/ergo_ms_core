# Настройка конфигурационных файлов

## Настройка .env

**Процедура конфигурации:**

1. Создайте файл `.env` на основе шаблона `.env.example`
2. Определите следующие параметры окружения:
   ```env
   # Общие настройки системы
   SYSTEM_TITLE=ERGO MS      # Название системы
   
   # Настройки API
   API_HOST=localhost        # Хост для API сервера
   API_PORT=8000            # Порт API сервера
   API_ALLOWED_HOSTS=localhost,127.0.0.1  # Разрешенные хосты
   API_DEPLOY_TYPE=development  # Тип развертывания (development/production)
   
   # Настройки токенов
   API_ACCESS_TOKEN_LIFETIME=30    # Время жизни access токена (в минутах)
   API_REFRESH_TOKEN_LIFETIME=1440 # Время жизни refresh токена (в минутах, 1440 = 1 день)
   
   # Ограничения запросов
   API_THROTTLE_RATES_ANON=10/minute  # Лимит запросов для анонимных пользователей
   API_THROTTLE_RATES_USER=5000/hour  # Лимит запросов для авторизованных пользователей
   
   # Безопасность
   API_SECRET_KEY=secret-key  # Секретный ключ (замените на сложный случайный ключ)
   
   # Настройки клиента
   CLIENT_HOST=localhost      # Хост клиентского приложения
   CLIENT_PORT=8001          # Порт клиентского приложения
   
   # Настройки почты
   EMAIL_HOST_USER=mail           # Адрес электронной почты, с которой будут высылаться коды
   EMAIL_HOST_PASSWORD=password   # Почтовый пароль для внешних приложений (НУЖЕН ПАРОЛЬ НЕ ОТ УЧЕТНОЙ ЗАПИСИ)
   EMAIL_HOST=smtp.mail.ru        # SMTP сервер
   EMAIL_PORT=465                 # Порт SMTP сервера
   EMAIL_USE_TLS=False
   EMAIL_USE_SSL=True

   VITE_DEFAULT_THEME=auto           # Тема: auto, light, dark
   VITE_LOG_LEVEL=debug             # Уровень логирования клиента
   ```

**Критичные параметры безопасности и производительности:**

- `API_SECRET_KEY`: в производственной среде требуется криптографически стойкий случайный ключ
- `API_DEPLOY_TYPE`: в производственной конфигурации устанавливается значение `production`
- `API_ALLOWED_HOSTS`: перечень доменных имён, авторизованных для обращения к API
- `API_THROTTLE_RATES`: лимиты частоты запросов определяются в соответствии с требованиями к пропускной способности
- Email-конфигурация: рекомендуется использование выделенной учётной записи электронной почты

## Настройка databases.yaml

**Процедура конфигурации:**

1. Создайте файл `databases.yaml` на основе шаблона `databases.yaml.example`
2. Спецификация структуры конфигурационного дескриптора:
   ```yaml
   databases:
    default:
      engine: "postgresql"
      name: "ergo_ms"
      user: "postgres"
      password: "admin"
      host: "localhost"
      port: 5432

    celery:
      engine: "postgresql"
      name: "ergo_ms_celery"
      user: "celery_user"
      password: "celery_password"
      host: "localhost"
      port: 5432
  
    celery_worker:
      engine: "postgresql"
      name: "ergo_ms_celery_worker"
      user: "celery_worker_user"
      password: "worker_password"
      host: "localhost"
      port: 5432
  
    celery_beat:
      engine: "postgresql"
      name: "ergo_ms_celery_beat"
      user: "celery_beat_user"
      password: "beat_password"
      host: "localhost"
      port: 5432

    analytics:
      engine: "mysql"
      name: "world"
      user: "root"
      password: "admin"
      host: "localhost"
      port: 3306
   ```

### Логика работы с базами данных для Celery

Система Celery использует приоритетную систему выбора конфигурации:

**CELERY WORKER (брокер и результаты):**
1. Сначала ищет секцию `celery_worker`
2. Если нет, ищет общую секцию `celery`
3. Если ничего нет — использует локальный SQLite

**CELERY BEAT (брокер):**
1. Сначала ищет общую секцию `celery` (чтобы использовать тот же брокер, что и Worker)
2. Если нет общей, ищет `celery_worker` (чтобы совпадало с Worker)
3. Если нет, ищет `celery_beat`
4. Если ничего нет — использует локальный SQLite

**CELERY BEAT (расписание):**
1. Сначала ищет секцию `celery_beat` (отдельная БД для расписания)
2. Если нет, ищет общую секцию `celery`
3. Если ничего нет — использует локальный SQLite файл

### Варианты настройки баз данных для Celery

**Вариант 1 (РЕКОМЕНДУЕТСЯ): Общая БД для всех компонентов**
- Создайте только секцию `celery`
- Worker и Beat будут использовать одну БД для брокера
- Расписание также будет храниться в этой БД
- Упрощает настройку и управление

**Вариант 2: Отдельные БД для Worker и Beat**
- Создайте секции `celery_worker` и `celery_beat`
- Worker использует `celery_worker` для брокера
- Beat использует `celery_worker` для брокера (чтобы задачи доходили до Worker)
- Beat использует `celery_beat` для хранения расписания
- Обеспечивает изоляцию компонентов

**Вариант 3: Локальный SQLite**
- Не создавайте секций или установите `CELERY_USE_LOCAL=true`
- Все данные будут храниться в локальных файлах
- Подходит для разработки и тестирования

### Настройка пользователей баз данных

**Вариант 1 (РЕКОМЕНДУЕТСЯ для разработки):**
Использовать одного пользователя для всех компонентов Celery. Можно использовать существующего пользователя `postgres`:
```yaml
celery:
  user: "postgres"
  password: "ваш_пароль_postgres"
```
Это упрощает настройку и не требует создания дополнительных пользователей.

**Вариант 2 (РЕКОМЕНДУЕТСЯ для продакшена):**
Создать отдельных пользователей для каждого компонента:
- `celery_user` — для общей очереди задач
- `celery_worker_user` — для воркеров
- `celery_beat_user` — для планировщика

Это обеспечивает лучшую изоляцию и безопасность.

**Создание пользователей в PostgreSQL:**

Если вы выбрали вариант 2, создайте пользователей в PostgreSQL:

```sql
-- Создание пользователей
CREATE USER celery_user WITH PASSWORD 'celery_password';
CREATE USER celery_worker_user WITH PASSWORD 'worker_password';
CREATE USER celery_beat_user WITH PASSWORD 'beat_password';

-- Создание баз данных
CREATE DATABASE ergo_ms_celery OWNER celery_user;
CREATE DATABASE ergo_ms_celery_worker OWNER celery_worker_user;
CREATE DATABASE ergo_ms_celery_beat OWNER celery_beat_user;

-- Предоставление прав
GRANT ALL PRIVILEGES ON DATABASE ergo_ms_celery TO celery_user;
GRANT ALL PRIVILEGES ON DATABASE ergo_ms_celery_worker TO celery_worker_user;
GRANT ALL PRIVILEGES ON DATABASE ergo_ms_celery_beat TO celery_beat_user;
```

**Если пользователи не созданы:**

Если указанные пользователи не существуют в PostgreSQL, система выдаст ошибку аутентификации. В этом случае:

1. **Создайте пользователей** (см. инструкции выше)
2. **Используйте существующего пользователя** (например, `postgres`) — замените `user` в конфигурации
3. **Используйте локальный SQLite** — установите переменную окружения `CELERY_USE_LOCAL=true` (данные будут храниться в файлах)

### Руководство по форматированию YAML

**Правила экранирования специальных символов:**

При редактировании YAML-дескрипторов строковые литералы, содержащие метасимволы синтаксиса YAML, подлежат обязательному заключению в двойные кавычки:

```
! : > | & * # { } [ ] ,
```

**Корректные примеры:**

```yaml
password: "!admin123"
hostname: "server.example.com"
query: "SELECT * FROM users"
path: "/home/user/data"
command: "grep -v '#' file.txt"
```

**Некорректная запись:**

```yaml
password: !admin123      # Ошибка: символ '!' интерпретируется парсером как YAML-тег
```

**Обоснование требования:**

YAML-спецификация определяет набор метасимволов синтаксиса. При отсутствии экранирования парсер ошибочно интерпретирует данные символы как элементы структуры документа, что приводит к нарушению семантической целостности конфигурации.

**Рекомендации по форматированию:**

- Строковые литералы, содержащие метасимволы, безусловно заключаются в двойные кавычки
- При наличии неопределённости относительно требования экранирования следует применять кавычки
- Пароли и прочие параметры безопасности требуют особого внимания к экранированию
- После модификации YAML-файлов рекомендуется верификация с использованием специализированного валидатора

## Настройка menu-order-config.json

Дескриптор `menu-order-config.json` определяет порядок отображения элементов навигационного меню клиентского приложения. Данный файл является опциональным; при его отсутствии система применяет конфигурацию по умолчанию, расположенную в `core/client/src/config/menu-order-config.json`.

**Процедура конфигурации:**

1. Создайте файл на основе шаблона:
   ```cmd
   copy menu-order-config.json.example menu-order-config.json
   ```

2. Спецификация структуры дескриптора:
   ```json
   {
     "menuOrder": [
       "User",
       "Settings",
       "BI"
     ],
     
     "separators": {
       "0": "Настройки",
       "2": "Модули"
     }
   }
   ```

3. Семантика параметров конфигурации:
   - `menuOrder`: упорядоченный массив идентификаторов маршрутов
   - `separators`: ассоциативный массив индексов элементов меню с соответствующими текстовыми метками разделителей

**Критичные требования:**

- Файл размещается в корневом каталоге проекта (на уровне `README.md`)
- После модификации файла требуется перезапуск сервера разработки
- Система осуществляет автоматический выбор конфигурационного дескриптора при инициализации
- При отсутствии пользовательского файла применяется конфигурация по умолчанию без генерации ошибок
- Идентификаторы маршрутов должны строго соответствовать определениям в модулях системы
- Индексация разделителей осуществляется с нулевого элемента

**Примеры конфигурации:**

*Переопределение порядка элементов меню:*
```json
{
  "menuOrder": [
    "BI",
    "User",
    "Settings"
  ]
}
```

*Добавление разделителей:*
```json
{
  "menuOrder": [
    "User",
    "Settings",
    "BI",
    "Reports"
  ],
  "separators": {
    "0": "Пользователь",
    "2": "Аналитика"
  }
}
```

**Верификация применения конфигурации:**

При инициализации сервера разработки система выводит диагностическое сообщение:
- `✓ Используется пользовательская конфигурация меню из корня системы` — обнаружен пользовательский дескриптор
- `✓ Используется стандартная конфигурация меню` — применяется конфигурация по умолчанию

## Возможность использования совместной работы на одном компьютере

Система поддерживает режим коллаборативной разработки посредством механизма совместного доступа к рабочей директории. Инициатор сеанса транслирует файловую систему проекта удалённым участникам, обеспечивая синхронное редактирование исходного кода.

**Технология реализации:** расширение [Live Share](https://visualstudio.microsoft.com/ru/services/live-share/) для Visual Studio Code/Cursor

**Процедура инициализации сеанса:**

1. Установите расширение из [официального репозитория](https://marketplace.visualstudio.com/items?itemName=MS-vsliveshare.vsliveshare)
2. Откройте проект в интегрированной среде разработки
3. Активируйте функцию «Live Share» посредством соответствующей кнопки интерфейса
4. Распространите сгенерированную ссылку участникам сеанса

Конфигурационный дескриптор `.vsls.json` автоматически применяется к сеансу, обеспечивая корректную видимость вложенных репозиториев и определяя область доступа участников.

**Детальная документация:** [официальное руководство Microsoft](https://learn.microsoft.com/en-us/visualstudio/liveshare/quickstart/share)

**Требование сетевой конфигурации:** для обеспечения полного функционала системы участникам сеанса требуется доступ к TCP-портам 8000 и 8001 (либо портам, определённым в `.env`). Порт 8001 обслуживает клиентское веб-приложение, порт 8000 — API-сервер.
