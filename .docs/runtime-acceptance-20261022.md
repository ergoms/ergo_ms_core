# Локальная приёмка runtime A/B — 22–23.10.2026

Host-профиль этапа A подтверждён на Windows/Linux: новые проекты с четырьмя
настоящими потребителями, PostgreSQL, полный setup и повторы без новых скачиваний.
Для B проверены установка обязательных моделей, индекс, локальные resolver-пути
и HF-инференс на CPU. Полная матрица остальных профилей и предметных сценариев
остаётся за пределами этой приёмки; ограничения и существующие ошибки указаны ниже.

## Состав и изоляция

Проверен существующий host-рецепт `setup-full` через `ergoms setup` на Windows 11
и Debian 12 в собственном Docker-контейнере WSL. Команда `setup` — штатный алиас
того же рецепта; прямой Windows `setup-full` требует администратора ещё в оболочке.
Защита привилегированных операций не ослаблялась. Windows-проект начинался без
venv, npm-пакетов, инструментов, моделей и download-кэша; сама ОС уже имела Git,
PowerShell, msiexec, 7-Zip и VC runtime. Это проверка нового проекта, не чистой ОС.

Использованы полные зафиксированные исходники CRM, education_materials_parser,
vacancies_parser и ollama_framework, включая настоящие Python/npm-зависимости.
Рабочие `.env`, БД и установленные зависимости не копировались. Каждой платформе
создан отдельный PostgreSQL-контейнер с собственными случайными реквизитами.
Профиль: host, portable Python/Node, PostgreSQL, локальный брокер, без nginx,
поиска, Jupyter и OS-служб; GPU скрыт. Обязательные модели: `deepvk/USER-bge-m3`
и `embeddinggemma:latest`. Необязательные модели не устанавливались.

Исходные ревизии: ergo_ms `fa93287c`, API `ccf4df8`, client `517d5bf`, media_api
`6e05fae`, CRM `6b3f325`, education_materials_parser `f024a99`, vacancies_parser
`1c1360d`, ollama_framework `cdb8588`. Поверх экспорта применены только перечисленные
ниже исправления. Архив содержит 4526 файлов; чужие локальные diff не включались.

WSL использовал временный канал к существующему localhost-прокси Windows.
Канал принимал только собственный QA-контейнер. TLS, firewall, глобальные прокси
и конфигурация WSL не менялись. В повторе HTTP(S)-прокси указывал на закрытый
`127.0.0.1:9`; подключение к собственной PostgreSQL оставалось доступным.
Это отказ HTTP-источников, а не полное отключение сети.

Опубликованная CRM `0168_finalize_incoming_ingress` требует подтверждения перехода
писателей. В новой Linux-БД проверены нулевые строки пяти связанных таблиц схемы
`m_crm`; старых процессов не было. `CRM_FINALIZE_INCOMING_INGRESS=1` задан только
в двух собственных QA-копиях. Миграция не менялась. Этот флаг не является
инструкцией обновления рабочей CRM: там нужен её штатный переход писателей.

## Контроль окончательного состава

Две новые установки из пустых проектов выполнены без возобновления после ошибок:
обёртка `483e02f`, API `9f3d8fd`, CRM `70351a8`; остальные исходные ревизии сохранены.
Экспорт содержит 4530 файлов. Новые БД, кэши и Python/npm-окружения независимы
от первоначальных QA-сред. До установки обе PostgreSQL-БД были пустыми, что
подтверждено отдельной SQL-проверкой. Обе установки и их повторы завершились кодом 0.

После этого настоящий CPU-инференс выявил native crash `0xC0000005` в Windows:
Transformers 5.16.1 при построении маски вызывал
`torch.cuda.graphs.is_current_stream_capturing` даже на CPU. В модуле добавлена
отдельная пара AttentionInterface/AttentionMaskInterface с явной SDPA-маской;
стандартные backend не подменяются. CUDA/GPU и Linux сохраняют прежний путь.
Дополнительный тест KAG также показал, что оболочка Windows скрывала ненулевой
код Django; исправлены три проксикоманды, проверены 0/7 для каждой.

Эти два runtime-исправления внесены в обе QA-копии из коммитов `b81edab` и `53315de`
после первых установок. Их присутствие в первоначальном холодном запуске не
заявляется. После внесения повторно проверены полный setup, неизменность runtime
и точные Git-версии всех 20 файлов кода/тестов на обеих платформах. Правки не меняют
рецепт установки или зависимости. Журналы и итоговый SHA256 receipt отделяют исходный
экспорт от проверенных после исправления ревизий.

| Проверка контрольной серии | Windows | Linux |
|---|---|---|
| Первый полный setup в пустом проекте | Код 0 | Код 0 |
| Первый повтор с отказом HTTP-источников | Код 0; 25 628 записей без изменений | Код 0; 24 058 записей без изменений |
| Повтор полного setup после runtime-исправлений | Код 0; 25 702 записи без изменений | Код 0; 24 128 записей без изменений |

В CPU-проверке три текста разной длины, включая пустой, дают конечные векторы
`[3, 1024]` с единичной нормой; пакетный результат совпадает с одиночными расчётами
при rtol=1e-4/atol=1e-5. Сравнение обычной Linux SDPA с новой явной маской на тех
же входах дало максимальное абсолютное отклонение 0.0. Это проверка этих входов,
а не доказательство численного тождества для любых моделей и данных.

Обязательные runtime-проверки отделены от дополнительных диагностик KAG.
Проверены API check, повтор migrate, четыре прежних install-алиаса, runtime-check,
model-check, повтор model-install, pip check, реальные DOCX/PDF/OCR/Chrome,
публичный конвертер CRM, 35 модульных тестов и 8 тестов HF.
Все 15 обязательных проверок каждой платформы вернули 0. Снимки сравнивались внутри
каждого повтора; инвентаризации разных стадий не смешиваются. Итоговый receipt
сверил 20 файлов кода/тестов с Git blobs на обеих платформах по SHA256, нормализуя
только CRLF/LF. Сравнение бинарников при повторе по-прежнему ограничено размером
и mtime. В журналах финального setup нет Traceback, FAILED или ERROR.

Linux-счётчики прокси контрольной установки и первого повтора совпали: 243 соединения,
7 712 054 212 принятых и 1 356 518 отправленных байт. Оба финальных повтора также
выполнялись с недоступным HTTP(S)-прокси `127.0.0.1:9`.

В штатный deployment unit-набор входят проверки конфликтующих деклараций и
совместимости прежних `use`/hook-файлов. Отказ основного источника, переход на
зеркало, повреждённый архив/checksum, короткий или прерванный ответ и откат неудачной
публикации проверены на локальных архивах и управляемом downloader. Это проверки
ветвей отказа, а не утверждение о доступности всех внешних зеркал в любой сети.

## Ограничения и доказательства

Штатная проверка `system-test --suite install --launch host` на Windows прошла
с кодом 0, кейс install_from_scratch — OK. Это дополнительный core-only профиль
host/SQLite с отдельным venv. В worktree переносились независимые Git-каталоги
зафиксированных QA-исходников: удалённый Git bootstrap не проверялся.
Первая попытка остановилась из-за отсутствия этих метаданных в экспортном fixture;
исправлялась только подготовка собственной QA-копии.
`--launch docker` запускался внутри QA-контейнера без Docker CLI/socket и дал
SKIP. Проверка полного Compose-стека, NSSM/systemd, portable PostgreSQL/Redis/nginx,
чистой ОС, GPU, инференса Ollama и всех предметных сценариев относится к следующей
приёмке. Обновление существующей рабочей установки и ремонт её старого npm-дерева
не проверялись. MSSQL/ClickHouse не проверены: отдельных серверов нет.

Полный архитектурный валидатор: прежние 5 ошибок размера документов CRM;
изоляция ядра/модулей, bridge-контракты и границы данных прошли. Чужие документы
не исправлялись. У LibreOffice Windows в отдельном CLI-smoke были предупреждения
XML/Python prefix, при этом текст PDF проверен. Публичный конвертер CRM прошёл отдельно.

Дополнительный полный набор KAG: 64 теста, 63 прошли, один упал на обеих ОС —
`PipelineTests.test_university_keeps_one_section_per_heading` (`test_pipeline.py:182`).
Тот же тест отдельно упал на исходной опубликованной ревизии `f024a99` на обеих ОС.
Pipeline и его тест не менялись; дефект не включён в эту серию. После исправления
оболочки Windows этот отрицательный прогон корректно возвращает код 1.
Тесты KAG используют SimpleTestCase и не создают БД; сам setup выполнял настоящие
миграции в двух собственных PostgreSQL-БД.
