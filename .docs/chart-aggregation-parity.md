# Сопоставление агрегаций SQL, файлов и клиента

Срез 23.10.2026, четвёртая поставка C. Это проверка существующего поведения,
а не утверждение об эквивалентности трёх движков. Общие входы находятся
в `core/api/src/core/analytics/tests/fixtures/aggregation_cases.json`.

## Метод проверки

15 таблиц: числовые и строковые значения, десятичная арифметика, целые за
пределами безопасного диапазона JavaScript, NULL/пустые категории, пустая
выборка, даты, timestamp со смещением, календарные границы, бины и неверный
диапазон. На каждой таблице проверены `sum`, `avg`, `count`, `ucount`, `min`, `max`.

SQL выполнялся настоящим PostgreSQL в новой уникальной `test_ergo_*` БД.
Диагностический loader подставлял подготовленную таблицу вместо чтения файла;
SQLAlchemy-выражения и полный `get_rows_for_chart` оставались настоящими.
SQL-исполнитель компилировал запрос PostgreSQL-диалектом и выполнял его через
Django cursor той же тестовой БД. Чужие подключения и рабочие БД не использовались.
Для SQL-пути отключался только файловый fast path. Отдельно выполнялся реальный
файловый путь на той же таблице с теми же описаниями полей.

Получены 90 наборов результатов SQL/файла и ещё 90 глобальных SQL-агрегатов.
Глобальная выборка нужна для корректного сравнения с клиентским индикатором:
среднее по всем исходным строкам нельзя сравнивать с отдельными групповыми средними.
Порядок строк SQL без `ORDER BY` нормализован только при сравнении; числовые
значения сравнивались как Decimal без округляющего допуска. SQL/file в этой
матрице имеют конечные десятичные средние, поэтому дополнительный допуск не нужен.

Клиент исполнялся Node 24.18.0. Загружался настоящий `chartDataTransform.js`
с настоящими `chartColors.js` и `measureVirtualFields.js`. Менялись только URL
импортов для разрешения extensionless-импорта Vite; тела функций не подменялись.
Проверены сырые строки и JSON-ответ SQL после настоящего DRF `JSONRenderer`.
Это Node-проверка вычислений и структуры рядов, не браузерная проверка ECharts.

## Подтверждённые расхождения и ограничения

| Сценарий | SQL / исходные данные | Клиент или другое исполнение |
|---|---|---|
| NULL в бине | `bin:4:-10:10`, строка `(amount=NULL, id=1)`, Y=count(id) | SQL относит строку к центру -7.5: PostgreSQL GREATEST/LEAST игнорируют NULL в ограничении номера корзины |
| NULL в count/avg сырых строк | Для контрольного числового поля SQL count=6, avg=2.583333… | `getIndicatorValue` считает 7 строк и avg=2.214285…; NULL входит в знаменатель |
| Все значения NULL | SQL sum/avg=NULL и count=0 | Та же функция на двух сырых строках даёт 0/0/2 |
| Пустой глобальный агрегат | Одна строка SQL с NULL/0 | Файловый путь возвращает пустой список |
| Запятая в строковом числе | SQL sum по `1,5`, `2.5` = 4.0 | Клиентский Number не читает `1,5`; сумма получается 2.5 |
| Большие исходные числа | SQL и файловая сумма `9007199254740993 + 1` = `9007199254740994` | Сумма Number получается `9007199254740992` |
| Большое число в JSON | SQL Decimal `9007199254740993` | DRF JSONRenderer уже передаёт числовое `9007199254740992`; потеря появляется до вычислений Node |
| Пустая строка и NULL категории | SQL хранит две отдельные группы | `getBarData` сводит обе подписи в `—`; итоговые значения складываются |

У `ChartIndicator.vue` есть прямое чтение единственной готовой строки сервера.
Поэтому результаты `getIndicatorValue` на сырых/многострочных данных не означают,
что штатный одиночный SQL-агрегат повторно пересчитывается компонентом.
Для bar/line текущие функции складывают значения при схлопывании измерений;
перенос средних/уникальных счётчиков на сервер требует полного описания группировки,
а не повторной суммы уже готовых агрегатов.

Небольшие отличия дробных Number отдельно классифицированы как IEEE 754 roundoff:
например, `0.1 + 0.2 - 0.3` вместо SQL Decimal 0 даёт около `5.55e-17`.
Потеря целых выше 2^53 не отнесена к этой допустимой дробной погрешности.

Дата группируется SQL до клиентского представления. Неделя начинается в
понедельник, проверены переход года, високосный февраль, месяц, квартал, год,
timestamp и NULL. Выбор auto-гранулярности сохраняет пороги 31/366/1095 дней.
У существующего timestamp-пути календарь остаётся wall time, не переводится
в UTC; новая универсальная политика часовых поясов этой поставкой не вводится.

## Перенесённая общая часть

В `src.core.analytics.aggregation` находятся финализация состояний агрегатов,
прежняя нормализация нефинитных float и разбор `bin:N:min:max` с ограничением
числа корзин 1–200. В `date_grouping` — преобразование даты, длина диапазона,
выбор auto-гранулярности и набор календарных единиц. Это скалярные совместимые
примитивы, без ORM, SQLAlchemy, Celery, NumPy или Polars.

SQL продолжает выполнять GROUP BY и агрегаты в источнике. Файловые группировки,
числовое приведение и накопители остаются в BI: их локальные Decimal-исправления
не включаются в коммит переноса. Переносятся только участки, которые по AST
совпадали в HEAD и рабочей копии. Все остальные функции двух адаптеров
остаются прежними; отдельно проверяется сохранность выбора источника.
Production-JavaScript, UI, ACL, схема БД и результаты сохранённых отчётов не меняются.

После переноса совпали все 90 результатов SQL/файла и 90 глобальных SQL-агрегатов
с исходным исполнением, включая прежние ошибки и fallback. Сопоставлялись также
фактические JSON-ответы. Это подтверждает совместимость переноса, а не устранение
вышеописанных расхождений.

## Последующие исправления C5/C6

Таблицы выше описывают исторический срез C4. NULL-бин исправлен в BI `ce8f2eb`,
пустой глобальный агрегат файла — `bfbe6a3`, AVG строкового поля — `ffb2d98`.
NULL остаётся отдельной группой; глобальный пустой агрегат возвращает одну
строку с NULL/нулевыми счётчиками. Строковый AVG в SQL применяет числовое
преобразование с десятичной запятой и пропускает некорректные значения.
Числовой AVG сохраняет штатное исполнение, включая малые экспоненты.

C5: 7 новых регрессионных тестов; полная копия BI — 157 тестов, OK, один SKIP;
чистые составы — 7/80 тестов. C6: 9 новых тестов; BI — 166, OK, один SKIP;
чистый состав — 89 тестов; 27 прежних SQL-выражений остались неизменны.
Проверки выполнялись на отдельных PostgreSQL-БД. Исходные 90/90 комбинаций
этой серией повторно не пересчитывались, поэтому старые количества не
представляют число оставшихся расхождений.

Точность Number/JSON, свёртка сырых индикаторов и схлопывание NULL/пустых
категорий ещё требуют согласованного контракта и отдельных изменений.
Новые расчёты не запускают пересчёт сохранённых отчётов.

## C8: группировка и точные числа

Воспроизведены слияние NULL/пустой строки/подписи «—», коллизии составных
подписей и значений цвета, потеря NULL-серии линии, сложение AVG вместо среднего,
неверный знаменатель среднего и COUNT по NULL, двоичная погрешность суммы,
потеря больших Decimal при JSON-сериализации. До правок семь новых клиентских
регрессионных тестов падали; новый тест библиотеки падал на отсутствии модуля.

Независимый `core.analytics.exact_aggregation` группирует подготовленные строки
по типизированным ключам и выполняет SUM/AVG/COUNT/COUNT DISTINCT/MIN/MAX.
Сумма сохраняет все десятичные разряды; среднее округляется HALF_EVEN до
не менее 28 значащих цифр и 16 дробных разрядов. Правило не зависит от текущего
Decimal context. Файловый адаптер BI передаёт только таблицу и спецификации.
Формулы, JOIN, даты/бины и фильтры продолжают использовать общий SQL-путь;
текстовые MIN/MAX также остаются в SQL, поскольку зависят от collation БД.
Нефинитные числовые значения превращаются в NULL до группировки и счётчиков.

Прежние ответы API сохраняются. Новый клиент явно запрашивает контракт:

- GET `/bi_analysis/bi_charts/<public_id>/rows/?aggregation_contract=decimal-v1`.
- POST `/bi_analysis/bi_datasets/<public_id>/rows-agg/` с прежним `fields`,
  `aggregation_contract: "decimal-v1"` и необязательным `chart_type`.

Ответ: `{rows: [...], aggregation: {version: 1, kind, dimensions, measures,
numeric_encoding: "decimal-string"}}`. Decimal и целые вне безопасного диапазона
JavaScript передаются строками; небольшие целые остаются числами. Неизвестная
версия и противоречащие объявления одного alias возвращают 400. Ссылки сортировки
на уже выбранное поле используют его агрегацию/гранулярность. Прежние 422/503
сохраняются. Доступ проверяется прежним слоем до чтения источника; отдельный
доступ к датасету для разрешённого графика дополнительно не требуется.

Сервис клиента раскрывает ответ в прежний массив и сохраняет происхождение
в неперечисляемом Symbol каждой строки. Готовые агрегаты не вычисляются повторно.
Скрытые измерения GROUP BY сохраняются отдельными категориями; частичные средние
и distinct-count не складываются без исходной статистики. Сырые строки используют
общие клиентские десятичные примитивы BigInt. Ключи групп отделены от подписей;
клик графика передаёт исходную категорию, включая NULL. Индикатор и обычные
axis/pie tooltips сохраняют точные строки. Фильтры готового ответа второй раз
к агрегированным значениям не применяются. Снимки отчётов не пересчитываются.

Общие контроли `exact_aggregation_cases.json` проверяют шесть операций на дробях,
больших числах, периодическом среднем, малых экспонентах, NULL и пустом входе:
36 случаев для SQL, 36 для файла и 36 для клиента. Дополнительно проверяются
группы, числовое приведение, даты, NULL-бины, реальные JSON и совместимость API.

Пределы: координаты ECharts остаются JavaScript Number; утраченные до BI разряды
числа Number восстановить нельзя. Все текстовые collation и внешний SQL кроме
PostgreSQL не объявляются проверенными. Остальные виды tooltip/оси могут
округлять отображение; числовые агрегаты и исходные точные строки сохраняются.
Большой локальный остаток стабилизации, включая выбор источника, в эту серию
не включается. Подробные результаты окончательного прогона — в core-analytics.md.
